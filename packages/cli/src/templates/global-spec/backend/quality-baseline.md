# 后端质量基线

> 机器级后端通用规则。项目级规则可以收紧或细化，但不要把具体项目事实反写到这里。

---

## 分层与职责

- 优先遵循项目已有 Controller、Facade、Service、Mapper、Repository 等分层，不跨层偷取职责。
- 新增接口前先查同域名、同资源、同动词的既有实现，避免制造平行入口。
- DTO、VO、Entity、Request、Response 的边界以项目级规则为准，不为了省事复用错误对象。
- 不要把临时兼容逻辑散落在多层；确实需要兼容时，要写清触发条件、退出条件和影响范围。

## 接口与错误处理

- 接口契约必须来自真实后端代码、文档或用户确认，不能凭字段名猜语义。
- 用户可见错误、业务异常和系统异常要按项目已有方式表达，不静默吞错。
- 新增校验时要明确失败提示、错误码或返回结构；不要只在下游兜底。
- 修改公共接口时要检查所有调用方、导出、测试和文档。

## 数据库与事务

- 修改查询条件、排序、分页、聚合或默认值前，先查同表、同字段和同业务口径的既有用法。
- 事务边界必须围绕真实一致性需求设置，不把无关读写塞进一个大事务。
- 批量操作要考虑幂等、重复提交、部分失败和日志可追踪性。
- 不要用静默空结果掩盖数据异常；是否允许空结果由项目级业务规则决定。

## 日志与验证

- 日志要服务排障，包含关键业务标识和失败原因；不要记录敏感信息。
- 文档或配置类后端变更至少跑 `git diff --check` 和相关文件存在性检查。
- 代码类后端变更按项目级 spec 执行编译、单测、集成测试或接口级验证。
- 如果检查失败来自既有问题，要记录失败命令和失败边界，不要把它包装成当前变更通过。
