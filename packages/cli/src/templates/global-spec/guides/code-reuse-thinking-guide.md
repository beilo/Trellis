# 代码复用思考指南

> **目的**：创建新代码前停下来想一想——它是否已经存在？

---

## 问题

**重复代码是不一致缺陷的第一来源。**

当你复制粘贴或重写已有逻辑时：
- 缺陷修复不会传播
- 行为会随时间逐渐分叉
- 代码库会变得更难理解

---

## 编写新代码前

### 第 1 步：先搜索

```bash
# 搜索相似函数名
grep -r "functionName" .

# 搜索相似逻辑
grep -r "keyword" .
```

### 第 2 步：提出这些问题

| 问题 | 如果是…… |
|----------|-----------|
| 是否存在相似函数？ | 使用或扩展它 |
| 这个模式是否在其他地方使用？ | 遵循现有模式 |
| 这是否可以成为共享工具？ | 在正确位置创建它 |
| 我是否在从另一个文件复制代码？ | **停下** - 抽取为共享代码 |

---

## 常见重复模式

### 模式 1：复制粘贴函数

**坏例子**：把验证函数复制到另一个文件

**好例子**：抽取到共享工具，并在需要处导入

### 模式 2：相似组件

**坏例子**：创建一个与现有组件 80% 相似的新组件

**好例子**：用属性/变体扩展现有组件

### 模式 3：重复常量

**坏例子**：在多个文件中定义同一个常量

**好例子**：单一事实来源，到处导入

---

## 何时抽象

**适合抽象的情况**：
- 相同代码出现 3+ 次
- 逻辑复杂到可能产生缺陷
- 多个人可能需要它

**不适合抽象的情况**：
- 只使用一次
- 平凡的一行代码
- 抽象会比重复更复杂

---

## 批量修改后

当你对多个文件做了相似修改后：

1. **评审**：是否捕捉到了所有实例？
2. **搜索**：运行 grep 查找是否有遗漏
3. **思考**：这是否应该被抽象？

---

## 陷阱：产生相同输出的不对称机制

**问题**：当两套不同机制产生同一组文件时，比如 init 使用递归复制，而 update 手动列出文件，目录变更可能通过一条路径传播，却在另一条路径中悄悄漂移。

**症状**：init 创建了预期结构，但 update 在旧路径创建文件或漏掉新文件。

**预防清单**：
- [ ] 重命名、移动或添加生成文件前，搜索所有引用旧结构的代码路径。
- [ ] 如果一条路径是自动推导的，另一条路径是手动列出的，在同一变更中更新手动列表。
- [ ] 如果项目有回归检查，添加或运行对比两套机制输出的检查。
