# 前端质量基线

> 机器级前端通用规则。项目级规则可以收紧或细化，但不要把具体项目事实反写到这里。

---

## 组件与目录

- 优先遵循项目已有组件组织方式，不要因为组件看起来可复用就提前抽到全局公共目录。
- 新组件应保持输入输出清晰，避免把请求、副作用、展示和业务编排全部塞进一个文件。
- 修改 UI 时先查相邻页面和同类组件，复用已有交互、空态、错误态和加载态表达。
- 不要把项目级样式约定写死为机器级规则；CSS Modules、全局 SCSS、组件库覆盖方式以项目 spec 为准。

## 样式类组合

- 多个样式类或条件样式类组合统一使用 `classnames`，不要用模板字符串或字符串拼接手写样式类列表。
- 只有单个静态样式类时才直接使用样式引用；一旦出现条件分支、多个样式类或空字符串兜底，就切到 `classnames`。
- 修改样式写法前先确认项目已有样式类组合工具；如果项目级规则指定了等价工具，以项目级规则为准。

## Hook 与状态

- Hook 只封装真实复用的逻辑；单点使用的短逻辑不强行抽 Hook。
- Hook 返回值要让调用方能清楚处理加载态、错误态、空态、成功态和重试。
- 涉及并发、重复点击、轮询、订阅或全局状态时，要明确清理时机和跨组件共享边界。
- 不要在 Hook 内静默吞掉用户可见错误，除非项目级规则明确要求。

## 类型与数据流

- 新增接口字段、枚举、状态值前，先查项目已有类型和 API 封装。
- 不要用 `any`、宽泛对象或空对象兜底掩盖不清楚的接口契约。
- 跨层数据映射要说明来源、默认值、异常值和消费方。
- 前端显示文案、权限、可见性和禁用态必须从明确的业务条件推导，不从猜测字段硬编码。

## 变更边界

- 扩展旧功能时，只在必要调用点接入新需求，不顺手扩大旧函数职责。
- 不要改动旧分支、旧入口或历史流程，除非 PRD 明确要求。
- 不要添加没有契约、需求或线上现象支撑的推测性 guard、fallback、catch-and-ignore 逻辑。
- 抽象必须让职责或边界更清楚；只为了少几行代码而隐藏无关行为，不要抽。

## 验证

- 文档或配置类前端变更至少跑 `git diff --check` 和相关文件存在性检查。
- 代码类前端变更按项目级 spec 执行 lint、type-check、单测或手工验证。
- 如果检查失败来自既有问题，要记录失败命令和失败边界，不要把它包装成当前变更通过。
